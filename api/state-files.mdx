## Overview

GSD uses several files to track runtime state, context, and interrupted work. These files are machine-generated and enable crash recovery and context preservation.

## STATE.md

Auto-generated cache of derived state. **Do not edit manually.**

### Generation

STATE.md is regenerated by reading:
- Milestone ROADMAP files
- Slice PLAN files
- Task SUMMARY files
- REQUIREMENTS.md counts

### Structure

```markdown
# GSD State

**Phase:** executing
**Active Milestone:** M001: Payment Integration
**Active Slice:** S02: Stripe Checkout Flow
**Active Task:** T03: Implement webhook handler
**Active Branch:** gsd/m001-s02

## Progress

**Milestones:** 0/3 complete
**Slices:** 1/5 complete
**Tasks:** 2/7 complete

## Requirements

**Active:** 12
**Validated:** 8
**Deferred:** 3
**Out of Scope:** 2
**Blocked:** 0
**Total:** 25

## Next Action

Execute T03: Implement webhook handler in slice S02.

## Blockers

- None

## Recent Decisions

- 2026-03-13: Use Stripe SDK instead of direct API calls
- 2026-03-12: Store webhook events in database for replay
```

### TypeScript Interface

```typescript
export interface GSDState {
  activeMilestone: ActiveRef | null;
  activeSlice: ActiveRef | null;
  activeTask: ActiveRef | null;
  phase: Phase;
  recentDecisions: string[];
  blockers: string[];
  nextAction: string;
  activeBranch?: string;
  registry: MilestoneRegistryEntry[];
  requirements?: RequirementCounts;
  progress?: {
    milestones: { done: number; total: number };
    slices?: { done: number; total: number };
    tasks?: { done: number; total: number };
  };
}

type Phase = 'pre-planning' | 'planning' | 'executing' | 
  'summarizing' | 'completing-milestone' | 'blocked' | 'complete';
```

<Warning>
  STATE.md is auto-generated. Manual edits will be overwritten on next state refresh.
</Warning>

## CONTEXT.md

Contains background information and dependencies for milestones and slices.

### Milestone CONTEXT.md

Provides background for planning a milestone.

```yaml
---
depends_on:
  - M001
  - M002
---

# M003 Context

## Background

This milestone builds on the authentication system (M001) and payment 
integration (M002) to implement subscription management.

## Dependencies

- M001 must be complete (JWT auth and user model)
- M002 must be complete (Stripe integration)

## Technical Context

- Use Stripe subscriptions API
- Store subscription status in user model
- Implement webhook handlers for subscription events

## Known Constraints

- Stripe webhooks require HTTPS in production
- Subscription changes take effect at period end
```

<ParamField path="depends_on" type="array">
  List of milestone IDs that must be complete before this milestone becomes active
</ParamField>

### Slice CONTEXT.md

Provides implementation context for a specific slice.

```markdown
# S03 Context

## What We're Building

Subscription upgrade/downgrade flow with proration.

## Key Files

- `src/routes/subscriptions.ts` - API endpoints
- `src/services/stripe.ts` - Stripe integration
- `src/models/subscription.ts` - Data model

## Architecture Notes

- Use Stripe subscription schedules for future changes
- Calculate proration on the client, apply on server
- Emit events for subscription changes (for analytics)

## Dependencies

- S01 (subscription creation) must be complete
- S02 (webhook handlers) must be working
```

## CONTINUE.md

Preserves state when work is interrupted. Enables crash recovery.

### Structure

```yaml
---
milestone: M001
slice: S02
task: T03
step: 3
total_steps: 5
status: interrupted
saved_at: 2026-03-13T14:30:00Z
---

## Completed Work

- Created webhook endpoint route
- Added Stripe signature verification
- Implemented event type routing

## Remaining Work

- Add database persistence for events
- Implement retry logic for failed handlers
- Add tests for webhook scenarios

## Decisions Made

- Store all webhook events raw in `webhook_events` table
- Process events asynchronously via job queue
- Use idempotency keys from Stripe event IDs

## Context

Working on webhook handler implementation. The signature verification 
is complete and working in tests. Need to persist events before 
processing them to enable replay on failure.

## Next Action

Create migration for `webhook_events` table with columns: id, event_id, 
event_type, payload (jsonb), processed_at, created_at.
```

### TypeScript Interface

```typescript
export interface Continue {
  frontmatter: ContinueFrontmatter;
  completedWork: string;
  remainingWork: string;
  decisions: string;
  context: string;
  nextAction: string;
}

export interface ContinueFrontmatter {
  milestone: string;
  slice: string;
  task: string;
  step: number;
  totalSteps: number;
  status: ContinueStatus;
  savedAt: string;
}

type ContinueStatus = 'in_progress' | 'interrupted' | 'compacted';
```

### Usage

CONTINUE.md is created automatically when:
- Task execution is interrupted (timeout, error, user cancellation)
- Agent explicitly calls "save progress" function
- Long-running task reaches checkpoint

On resume, GSD:
1. Reads CONTINUE.md
2. Passes full context to agent
3. Agent reads "Completed Work" and "Next Action"
4. Continues from checkpoint
5. Deletes CONTINUE.md when task completes

<Tip>
  CONTINUE.md enables true crash recovery. If the agent process dies, restarting picks up exactly where it left off.
</Tip>

## UAT.md

User Acceptance Testing plan and results for slice verification.

### Structure

```markdown
# S02 UAT Plan

## UAT Type

**UAT mode:** live-runtime
**Verification approach:** API testing with real backend
**Duration estimate:** 15 minutes

## Test Scenarios

### Scenario 1: Happy path webhook

**Setup:**
- Start local server
- Use Stripe CLI to forward webhooks

**Steps:**
1. Create test customer in Stripe dashboard
2. Trigger `customer.created` event
3. Verify webhook received
4. Check event stored in database

**Expected:**
- Webhook handler returns 200
- Event persisted with correct event_id
- Processing completed within 5 seconds

### Scenario 2: Invalid signature

**Setup:**
- Server running
- Manual curl with invalid signature

**Steps:**
1. Send POST to `/webhooks/stripe` with fake signature
2. Check response

**Expected:**
- Returns 400 with "Invalid signature" error
- No database persistence
- Error logged

## Results

**Status:** passed
**Tested at:** 2026-03-13T15:00:00Z
**Tested by:** GSD Auto

### Scenario 1: ✅ PASSED
- All webhooks received correctly
- Database persistence working
- Average processing time: 234ms

### Scenario 2: ✅ PASSED
- Invalid signatures properly rejected
- No false positives in 10 test attempts
```

## SECRETS.md

Secrets manifest for API keys and credentials needed by a milestone.

### Structure

```markdown
# Secrets Manifest

**Milestone:** M001
**Generated:** 2026-03-13T10:00:00Z

### STRIPE_SECRET_KEY

**Service:** Stripe
**Dashboard:** https://dashboard.stripe.com/apikeys
**Format hint:** Starts with `sk_test_` or `sk_live_`
**Status:** pending
**Destination:** dotenv

1. Go to Stripe Dashboard → Developers → API keys
2. Copy the "Secret key" (not publishable key)
3. For testing, use test mode keys (sk_test_...)

### STRIPE_WEBHOOK_SECRET

**Service:** Stripe
**Dashboard:** https://dashboard.stripe.com/webhooks
**Format hint:** Starts with `whsec_`
**Status:** collected
**Destination:** dotenv

1. Go to Stripe Dashboard → Developers → Webhooks
2. Add endpoint: https://yourdomain.com/webhooks/stripe
3. Copy the signing secret
```
