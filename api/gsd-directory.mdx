## Overview

The `.gsd/` directory is the source of truth for all GSD project state. Every file in this directory is machine-readable and human-editable, following a structured markdown format with YAML frontmatter.

## Directory Structure

```
.gsd/
├── PROJECT.md           # Project definition and requirements
├── STATE.md             # Current derived state (auto-generated)
├── DECISIONS.md         # Engineering decision log
├── REQUIREMENTS.md      # User requirements by status
├── QUEUE.md             # Queued changes and suggestions
└── milestones/
    └── M001/            # Milestone directory (bare ID)
        ├── M001-ROADMAP.md    # Milestone roadmap
        ├── M001-CONTEXT.md    # Milestone context
        ├── M001-RESEARCH.md   # Research findings
        ├── M001-SUMMARY.md    # Completion summary
        ├── M001-SECRETS.md    # Secrets manifest
        └── slices/
            └── S01/           # Slice directory (bare ID)
                ├── S01-PLAN.md       # Slice plan
                ├── S01-CONTEXT.md    # Slice context
                ├── S01-RESEARCH.md   # Slice research
                ├── S01-SUMMARY.md    # Slice summary
                ├── S01-CONTINUE.md   # Interrupted work
                ├── S01-UAT.md        # Verification plan
                └── tasks/
                    ├── T01-PLAN.md       # Task plan
                    └── T01-SUMMARY.md    # Task summary
```

## Root Files

### PROJECT.md

Defines the project vision, tech stack, and core requirements.

<ParamField path="PROJECT.md" type="markdown">
  Human-editable project definition created at initialization
</ParamField>

**Structure:**
- Project name and vision
- Tech stack and dependencies
- Success criteria
- Initial requirements

### STATE.md

Auto-generated cache of derived state. **Do not edit manually.**

<ResponseField name="STATE.md" type="markdown">
  Generated by reading roadmap and plan files. Recreated on every state refresh.
</ResponseField>

**Contents:**
- Active milestone, slice, and task
- Current phase
- Progress counters
- Next action
- Blockers

### DECISIONS.md

Chronological log of engineering decisions with context and rationale.

<ParamField path="DECISIONS.md" type="markdown">
  Append-only decision log. Each entry includes timestamp, context, and decision.
</ParamField>

**Entry format:**
```markdown
## YYYY-MM-DD: Decision Title

**Context:** What led to this decision

**Decision:** What was decided

**Rationale:** Why this approach

**Alternatives considered:** What else was evaluated
```

### REQUIREMENTS.md

Structured user requirements organized by status.

<ParamField path="REQUIREMENTS.md" type="markdown">
  Requirements document with sections for Active, Validated, Deferred, and Out of Scope
</ParamField>

**Sections:**
- **Active** — Currently being implemented
- **Validated** — Implemented and verified
- **Deferred** — Postponed to future milestones
- **Out of Scope** — Explicitly excluded

### QUEUE.md

Temporary holding area for user requests and suggested changes.

<ParamField path="QUEUE.md" type="markdown">
  Incoming requests that haven't been triaged yet
</ParamField>

## Milestones Directory

Each milestone gets its own directory: `.gsd/milestones/M001/`

### Naming Convention

Directories use **bare IDs** (M001, M002), while files use **ID-SUFFIX** format (M001-ROADMAP.md, M001-CONTEXT.md).

Legacy descriptor-suffixed names (M001-PAYMENT-SYSTEM/) are supported via prefix matching for backward compatibility.

## Path Resolution

GSD uses a flexible path resolver that supports both current and legacy naming conventions:

### Directory Resolution
1. Exact match (M001)
2. Prefix match (M001-SOMETHING) for legacy projects

### File Resolution
1. Direct match: `ID-SUFFIX.md` (M001-ROADMAP.md)
2. Legacy descriptor: `ID-DESCRIPTOR-SUFFIX.md` (T03-INSTALL-PACKAGES-PLAN.md)
3. Legacy bare: `suffix.md` (roadmap.md)

<Tip>
  New projects use bare IDs for directories and ID-SUFFIX for files. Legacy projects work without migration.
</Tip>

## State Derivation

GSD derives current state by reading files on disk. The STATE.md file is just a cache.

**Derivation order:**
1. Scan `.gsd/milestones/` for milestone directories
2. Read each ROADMAP.md to check completion
3. Find first incomplete milestone with satisfied dependencies
4. Read PLAN.md to find first incomplete task
5. Check for CONTINUE.md (interrupted work)
6. Determine phase and next action

<Note>
  **Important:** Files on disk are the source of truth. STATE.md is regenerated on every refresh.
</Note>

## File Locking

GSD uses lock files to prevent concurrent modification:

- `.gsd/.lock` — Main process lock
- `.gsd/milestones/M001/slices/S01/.lock` — Slice execution lock

**Lock format:**
```json
{
  "pid": 12345,
  "timestamp": "2026-03-13T10:30:00Z",
  "phase": "executing",
  "milestone": "M001",
  "slice": "S01",
  "task": "T03"
}
```

## Working with .gsd/ Files

All `.gsd/` files are designed to be both machine-readable and human-editable.

<Steps>
  <Step title="Edit project definition">
    Modify `PROJECT.md` to update project vision or tech stack
  </Step>
  <Step title="Log decisions">
    Append to `DECISIONS.md` when making architectural choices
  </Step>
  <Step title="Update requirements">
    Move items between sections in `REQUIREMENTS.md` as status changes
  </Step>
  <Step title="Never edit STATE.md">
    STATE.md is auto-generated. Changes will be overwritten.
  </Step>
</Steps>
